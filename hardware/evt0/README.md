# Gen1 EVT-0 hardware lock

This directory holds machine-readable inputs for the production-equivalent single-unit build.

- `bom-lock.csv` is the pre-release line-item ledger. `applicability` separates common, integrated-mainboard and custom-board rows; `planned_buy_qty_when_unblocked` is a future planning quantity, not a current purchase instruction.
- `bom-revisions/` binds a BOM revision to the line-ledger hash, target-binding hash, target identity, evidence selectors, receipts and approval. Only applicable `ALL + activeBranch` rows participate in a release.
- `purchase-plan.csv` is the executable single-buy queue. Its status and purchase gate prevent board-dependent parts from being ordered before `BOARD_TARGET` is frozen.
- `LOCKED` requires an exact manufacturer part number, revision/source evidence, incoming checks and approval against the EVT-0 target.
- `CANDIDATE` is selected for engineering review but is not yet approved for PCB release.
- `BLOCKED` means missing evidence prevents schematic/layout release.
- Any later substitution creates a new BOM revision and reruns the affected EVT-0 gates.
- `evidence-sources.json` records source grades, retrieval status, hashes, claim scope and physical verification gates.
- `build/hardware-evidence-refresh.json` is generated by `npm run refresh:hardware-evidence`; it rechecks the locked OID source hashes without promoting web claims to physical facts.
- `board-evidence-matrix.csv` keeps public reference architectures and supplier inquiry leads separate from real `BOARD_TARGET_CANDIDATE` rows.
- `firmware-readiness-matrix.csv` gates the Rust execution route, C ABI, two-board boot, peripheral reach, reproducible build and C/Rust differential.
- `rust-firmware-evidence.json` pins the upstream Rust/OpenVela/ESP/audio/storage evidence to exact Git commits and content hashes.
- `golden-24/` owns the 24-code logical product fixture; physical codes stay unassigned until the target code tool is frozen.
- `snapshot-v1/` contains the device snapshot schema, design fixture and RFC 8785 golden vectors.
- `intake-v1/` contains exact-SKU benchmark and two-sample board/OID intake templates.
- `benchmark-seller-evidence-v1/` keeps consumer benchmark seller originals separate from MB1 replies and received-unit intake. Profiles lock source ID/grade/bytes/SHA-256, while record-bound raw paths and a continuous-video gate prevent different SKUs or pending items from being mixed. Its complete state only means ready for human evidence review.
- `vendor-evidence-v1/` structures M01-M08, ten attachments, two offered-sample identities and file hashes. Its `outbound-v1/` compiles a deterministic manual-send bundle that remains `PREPARED_NOT_SENT`; `READY_TO_BUY` remains a vendor-claim payment gate and never freezes `BOARD_TARGET`.
- `vendor-contact-receipts-v1/` binds one manual submission to an immutable outbound bundle, same-day official-entry evidence and actual send/confirmation artifacts. `AWAITING_RESPONSE` has no payment or target-binding effect.
- `lab-v1/` contains the reusable instrument registry schema, one six-slot/seven-asset capture plan, physical-asset identity/calibration/reference evidence, measurement-method catalog and session template. PnP discovery and prepared workspaces have no qualification effect and record evidence without guessing a board target.
- `evidence-capture-v1/` is the shared raw-byte capture adapter for Vendor Contact, Benchmark Seller, Lab Registry and Vendor Response. It writes only a destination-exclusive raw copy and one immutable capture index; owner drafts remain unchanged and must be updated/revalidated explicitly by their owners.
- `hardware-system-v1/` separates the stable 12-block/18-interface topology from the current target selector, evidence bindings and EDA entry state.
- `device-link-v1/` freezes host/device install semantics independently from the future physical transport profile.
- `test-result-v1/` records raw latency samples, specimen/tool identities, synchronization and recalculated verdicts.
- `platform-ffi-v1/` freezes the single-owner C ABI, explicit layouts, queue-loss evidence, audio timestamp class, durable-storage contract and shared C/Rust vectors.
- `board-port-evidence-v1/` is the exact supplier/board-port evidence request and two-board execution order.
- `build/jlceda-bridge-status.json` is generated by `npm run eda:doctor`; it records the local JLCEDA/MCP read-only bridge, loopback-only listener and connection evidence. A passing bridge does not freeze `BOARD_TARGET`.
- `build/jlceda-mcp-singleton.json` is generated by `npm run eda:singleton`; it records every `easyeda-mcp-pro` process on ports 49620–49629 and identifies fallback-port split before live MCP results are used as design evidence.

The controlling specifications are [HardwareSystem v1](../../docs/hardware-system-architecture.md) and [Gen1 EVT-0 single-unit target sample](../../docs/hardware-gen1-p0.md). The current supplier action is the [MB1 prepay inquiry pack](../../docs/research/gen1-mb1-prepay-pack.md).

## Evidence refresh

```powershell
npm run refresh:hardware-evidence
```

The command re-fetches `SRC-OID-*` official pages/APIs and compares HTTP status, response byte count and SHA-256. A drift means the source changed and requires re-archiving and review; it does not establish a board MPN, OID-head revision or production suitability.

```powershell
npm run eda:doctor
```

The EDA doctor verifies the installed JLCEDA Pro executable, pinned Node/MCP runtime, Codex read-only scopes, loopback listener and two established loopback endpoints. The extension must be imported and connected in JLCEDA Pro before the last connection check can pass; external listeners and ordering stay disabled.

```powershell
npm run eda:singleton
```

Run this read-only inspection when multiple Codex threads are open. The intended evidence state is one MCP process on configured port `49620`; fallback listeners are recorded as a runtime integration gap rather than a board-design fact.

```powershell
npm run validate:hardware-lab
```

This validates the reusable EVT-0 lab baseline package. It checks method/instrument references and template boundaries; it does not manufacture physical results or freeze `BOARD_TARGET`.

```powershell
npm run discover:hardware-lab
```

This writes a PnP/serial lead report to `build/hardware-lab-discovery.json`. It is explicitly discovery-only;
instrument qualification still requires nameplate/serial artifacts plus calibration certificate or traceable self-check evidence.

```powershell
npm run prepare:hardware-lab-registry -- --registry-id EVT0-LAB-REGISTRY-<UNIQUE-ID>
```

This creates a pending-only workspace under `build/hardware-lab/instruments/<registry-id>/` with a source-hash manifest,
six-slot/seven-asset draft, raw directory and capture checklist. It does not write a registry record or change payment,
qualification, BOM or target-binding state.

```powershell
npm run prepare:benchmark-seller-evidence -- --profile-id REF2-BABYBUS-G4-446637-SAME-ITEM-V1 --record-id REF2-SELLER-EVIDENCE-<UNIQUE-ID>
npm run validate:benchmark-seller-evidence
```

The prepare command creates a pending-only REF2 seller request, source-hash manifest, draft and record-exclusive raw directory. The validator checks source-baseline drift, physical-versus-retail evidence roles, file confinement, bytes/SHA-256, same-item continuous video, cross-record reuse and status-only promotion. Neither command sends a message, authorizes payment, mutates the purchase plan, creates intake evidence or changes `BOARD_TARGET`.

```powershell
npm run refresh:vendor-contact-sources
npm run validate:vendor-outbound
npm run validate:vendor-contact-receipts
```

These commands build and byte-check the MB1 manual outbound bundle, then validate the separate submission-receipt contract and its file-tamper self-test. They do not send messages or create supplier replies.

```powershell
npm run validate:vendor-evidence
npm run validate:bom-revision
npm run validate:hardware-rd
```

The first command validates the supplier-response payment gate; the second validates branch-aware BOM revision links. `validate:hardware-rd` runs the reusable hardware contract and host-test bundle in one command. A green result preserves unresolved physical gates rather than promoting empty templates.

## Raw evidence capture

`evidence-capture-v1` requires request-relative, normalized source paths and explicit `mediaType`,
`capturedAt`, `sourceUrl` and lane route metadata. It refuses source links, path escapes, owner identity
drift, case-folded collisions, existing destinations and index replacement. Use:

```powershell
npm run preflight:hardware-evidence -- --lane VENDOR_CONTACT --workspace build/vendor-contact-receipts/20260804-ZTRON-01
npm run capture:hardware-evidence -- --request build/vendor-contact-receipts/20260804-ZTRON-01/capture-request.CAPTURE-ID.json
npm run check:hardware-evidence -- --request build/vendor-contact-receipts/20260804-ZTRON-01/capture-request.CAPTURE-ID.json
npm run test:hardware-evidence-capture
npm run validate:hardware-evidence-capture
```

The adapter does not create Message-ID, supplier response, instrument qualification, purchase approval,
five-tuple values or `BOARD_TARGET` state.
## Reusable test-fixture architecture v1

`hardware/evt0/test-fixture-v1/` adds a target-neutral, versioned seam from the
stable fixture profile through an unresolved target adapter and pending physical
fixture/selftest into the existing `lab-v1` session, `TestResult v1`,
`evidence-capture-v1`, and ReleaseGate owners. It does not replace or duplicate
those owners.

The package fixes eight capability IDs and partitions the 18 stable topology
interfaces across seven operational families. `IF-USB-DATA`, storage power-loss
durability, and control/status remain explicit coverage gaps. `BOARD_TARGET`
stays `UNRESOLVED`; no voltage/current, pin, connector, pogo, or mechanical
target values are declared. Templates and selftests have no physical promotion
effect.

Topology references use the existing canonical identity rule
`canonicalSha256(topologyHashInput(topology))` with `topologyId` omitted from the
hash input; the raw topology file SHA-256 remains separate provenance. The
targeted validator is `117/117`; its negative selftest is `109/109` baseline plus
`40/40` rejected mutations.

The read-only software boundary is task-name independent: the current software
owner anchor is hashed and recorded alongside the newest formal report
(`SW-AUTHORING-TASK-RECOVERY-01` report 22/22), while the explicit
hardware-impact report remains the authority for `hardwareImpact=NONE`,
`BOARD_TARGET=UNRESOLVED`, `sessionCoreModified=false`,
`familyWorkspaceModified=false`, `productionProviderQualified=false`, and
`offlineReady=false`. No software or software-owner file is written by this
package.

Validate the package with:

```powershell
npm run validate:hardware-test-fixture
npm run test:hardware-test-fixture
```

## Fixture method-gap evidence audit

`hardware/evt0/method-gap-evidence-v1/` revision `1.1.0` is a source-capture-only audit for
three explicit coverage gaps: dedicated `IF-USB-DATA` transport observation,
`IF-STORAGE` power-loss durability, and `IF-CONTROL`/`IF-STATUS` HIL stimulus
and observation. It does not edit the stable nine-method catalog or the
accepted fixture package, and its proposed method IDs remain
`PROPOSED_ONLY`.

The package captures public official source snapshots with URL, publisher,
retrieval time, version/date, HTTP status, content type, byte count, SHA-256,
raw path and claim boundary. USB and control/status receive
`FREEZE_TARGET_NEUTRAL_SKELETON`; storage remains
`KEEP_PENDING_MORE_PRIMARY_EVIDENCE` because target storage technology,
filesystem, recovery semantics and thresholds are unresolved. All target
parameters and physical acceptance thresholds remain `PENDING`.

```powershell
npm run validate:hardware-method-gap-evidence
npm run test:hardware-method-gap-evidence
```

The validator rechecks the canonical topology identity, stable owner references,
the nine raw snapshot bytes/SHA-256 values, live fixture capability/interface/
gap semantics, task-name-independent software read-only boundaries and
no-promotion effects. Audit-time dependency hashes remain provenance rather than
permanent live-byte requirements. Reports are ignored build outputs; no physical
fixture, method-catalog entry, instrument registration, target binding or
ReleaseGate decision is created. The package result is `26/26`; its negative
selftest baseline is `26/26` with `23/23` mutations rejected.
